# 从 L1 到 L3：一个 AI 自主开发方案

**以一个 Flutter 加 Python 项目为例，把 Berkeley RDI 的软件自主开发三级框架落成一套可执行的工程方案，覆盖需求、架构、界面、计划、开发、测试、部署七个阶段。**

第一部分讲为什么这么设计，第二部分讲怎么把它建出来，附录放术语、验证记录和可运行文件。

> **适用范围与时效**
>
> 本文基于 2026 年 8 月的工具状态写成。文中引用的开源项目版本会变，其中设计系统规范当时仍标注为 alpha，采用前请核对上游现状。
>
> 本文是一份设计方案加一次小规模验证，不是有产出数据的案例研究。L1 的规约层与执行器、L1.5 的风险分级 / R0 自动合并 / 审计包，均经 kite 项目实测落地（见各章「落地现状」与 [复盘](./retro-2026-08-07-l1-foundation.md)）；L2 的验证体系设计完整但尚未跑满一个观察窗口，L3 只搭了机制没有实跑。
>
> **一处消歧**：本文的 L1 到 L3 指人类关卡在循环上的位置，与循环工程里衡量单条循环成熟度的就绪度分级不是一回事。一条就绪度很高的循环，仍然可能只被允许处理 L1 级别的变更。

# 第一部分　为什么这么设计

## 少掉的一个轴

Berkeley RDI 那篇《当编程不再是瓶颈》提出了软件自主开发的三个等级：**代码自主**（AI 全权实现，人按 pull request 审查并掌控部署）、**流水线自主**（人既不写也不审代码，只提高层需求）、**需求自主**（AI 自己决定该做什么）。它对标 SAE 的自动驾驶分级，目的是让能力宣称、部署选择和问责机制都清晰可辨。

这个框架是本文整套方案的骨架。但把它压到一个真实形态的项目上，会立刻撞上一堵墙。

本文的样板产品叫 Kite，一个个人 AI 助理：语音或文字速记，自动结构化为笔记、任务、日程；本地优先，离线可写；自然语言检索与追问。客户端是 Flutter 双端，后端是 Python，分成 Agent 编排层和 API Server。

按 Berkeley 的定义，第二级要求“AI 跑通从设计、实现到测试、审计、部署的整个流水线”。设计、实现、测试、审计这四件事可以做到无人介入。部署这一件做不到，而且不是因为技术不够。

后端是有状态的长连接服务，单副本部署时重启会瞬间断开所有在线会话。客户端二进制受应用商店审核，一次错误发布的回滚周期以天计。这两件事都不是“验证做得更好就能解决”的问题，它们是撤销成本的问题。

所以第二级必须拆开。**Berkeley 的三级衡量的是“AI 拥有多少生命周期”，但一个系统能让 AI 拥有多少，取决于出错之后多久能回到上一个已知良好状态。**

## 撤销成本决定你能放权到哪一级

### 等级就是人类关卡的位置

在动手拆之前，先把等级这个词说准。它不是一个程度副词，是一个可以指着看的东西：**人类关卡在循环上的位置。**

一条完整的开发循环从意图开始，经过需求、契约、实现、验证、合并，最后到发布，然后由线上反馈回到意图。这条环上人能站的位置只有三处：

| 关卡 | 人在这里做什么 | 由什么决定它能不能关 |
| --- | --- | --- |
| 需求接受 | 判断这条需求该不该做、边界对不对 | 意图能否被规约完整捕获 |
| PR 合并 | 判断这次改动对不对 | 验证链够不够强 |
| 发布按钮 | 判断这次上线值不值得冒险 | 撤销成本高不高 |

等级就是这三道门依次关上的过程：

| 等级 | 人站在哪 | 循环长什么样 |
| --- | --- | --- |
| L1 | **PR 合并** | 发现 → 契约 → 实现 → 验证 → PR → **人** → 合并 |
| L1.5 | PR 合并，但只对一部分变更出现 | 同上，人按风险抽样出现 |
| L2 | **需求接受** | 意图 → **人接受需求** → 契约 → 实现 → 验证 → 合并 |
| L3 | 循环内已无关卡 | 遥测 → 需求候选 → 契约 → 实现 → 验证 → 合并 → 遥测 |

L3 那一行容易被误读。**人不是消失了，是被挪到循环外面去了**：他维护宪章、做月度审计、随时能拉闸，但这些动作不在循环的路径上。Berkeley 说的“人在这个循环开发中的最终角色消失了”，指的正是这个。

**只有三级，不是因为分类学上分了三类，是因为只有三道门可关。**

### 两个轴

有了关卡视角，Berkeley 那个框架的问题就不用靠举例来说明了，可以直接推出来：**它的第二级同时关掉了 PR 合并和发布按钮两道门。**

这两道门的开关条件完全不同。PR 那道由验证链的强度决定，发布那道由撤销成本决定。捆在同一级里，就必然出现“验证够格了但发布不能放手”的死结，而这恰恰是绝大多数有状态服务的真实处境。

所以要把原来的一个等级拆成两个独立定级的轴：

**合入自主**：从意图到代码合入主干这一段，人参与到什么程度。沿用 Berkeley 的 L1 / L2 / L3，中间补一级 L1.5。

**发布自主**：从主干到生产运行这一段，人参与到什么程度。另设 D1 / D2 / D3，同样在 D1 与 D2 之间补一级 D1.5。

| 等级 | 合入自主 | 发布自主 |
| --- | --- | --- |
| 1 | Agent 实现，人评审契约与 PR | 一键触发，自动探活与回滚，人点按钮 |
| 1.5 | 按风险分级抽审 | 低风险变更自动放行，其余人点 |
| 2 | 无人评审代码，靠确定性门禁 | 自动金丝雀放量 + 指标自动回滚 |
| 3 | Agent 自主提需求 | Agent 自主决定发布节奏 |

### 一个数推出整张表

两个轴看起来像是多了一层复杂度，其实是简化：**每一类变更的等级上限，由它的撤销成本单独决定。**

| 变更类型 | 所在轴 | 撤销动作 | 撤销成本 | 等级上限 |
| --- | --- | --- | --- | --- |
| 代码合入主干 | 合入 | revert 一个提交 | 接近零 | **L2** |
| 服务端下发的页面编排与文案 | 发布 | 改配置，下次拉取生效 | 秒级 | **D2** |
| 特性开关 | 发布 | 关掉开关 | 秒级 | **D2** |
| Agent 提示词与工具定义 | 发布 | 改配置，秒级生效 | 配置秒级，但已生成的回答收不回来 | **D1.5** |
| 服务端进程代码 | 发布 | 重启回滚，打断在线会话 | 分钟级且有损 | **D1** |
| 客户端二进制 | 发布 | 重新发版走审核 | 天级 | **D1**，永久 |

第四行是唯一需要解释的一格。改提示词和改文案都是改配置、都能秒级回退，但**撤销成本要算上已经外溢的副作用**：文案回退之后没有人受影响，提示词回退之前生成的那些回答已经到了用户手里。所以它比另外两类秒级变更低一档，可以自动放行，但必须带影响面上限（灰度比例、单位时间调用数）。

L 与 D 是两把刻度，不能互相换算：L2 说的是没人看代码，D2 说的是没人点发布，两者可以同时成立，也可以一高一低。这一列给的是上限，不是现在走到哪。

拿到这张表，Kite 的目标位就自动落下来了：

- 后端非核心逻辑：**合入 L2 / 发布 D1**
- 后端认证、计费、数据迁移：**合入 L1 永久 / 发布 D1**
- 客户端二进制：**合入 L1.5 / 发布 D1 永久**
- 服务端下发的页面、文案、开关：**合入 L2 / 发布 D1.5，试点 D2**

### 这条推论反过来指导架构

如果撤销成本决定上限，那么**提升自主性最有效的手段不是加验证，是降低撤销成本**。

具体到 Kite，就是这条看起来只是性能优化的决定：把页面编排、文案、校验规则、实验配置全部改成服务端下发（服务端驱动 UI），客户端只负责渲染一组稳定的原子组件。

它的真实价值不是让改文案更快。它是在一个撤销成本普遍很高的系统里，人为制造出一块撤销成本接近零的地皮，让发布自主有地方可以生长。没有这块地皮，发布侧永远只能停在 D1，整套体系被最慢的一环卡死。

代价是客户端的渲染器本身成为高危模块，按最严格等级管理。这笔交易是划算的：把不确定性从“每一次业务变更”集中到“一个很少改动的渲染器”。

### 升级不是宣布，是走流程

每一级都有出口准则（后面各章分别给出），但达标只是允许提升，不是已经提升。中间还有一步：**影子运行**。

新等级的流程照跑，但人审仍然保留，比对两者判定的一致性，达到 90% 才正式切换。这一步适用于每一次升级，L1 到 L1.5、L1.5 到 L2 都一样。它让“去掉人审安全吗”变成可测量的，而不是靠信心。

### 让撤销成本变成会阻断构建的东西

到这里为止，撤销成本还只是一个用来推导目标位的判断。要让它真正起作用，必须有东西在运行时读它，否则它就是一个读完点头、工程上无处安放的概念。

做法是一份进版本库的登记表，按路径登记每类变更的撤销代价：

```yaml
# reversibility.yaml
- pattern: "apps/mobile/lib/**"
  undo: 重新发版走审核
  latency: 天级
  side_effects_reversible: true
  ceiling: D1

- pattern: "config/sdui/**"
  undo: 改配置，下次拉取生效
  latency: 秒级
  side_effects_reversible: true
  ceiling: D2

- pattern: "config/prompts/**"
  undo: 改配置，秒级生效
  latency: 秒级
  side_effects_reversible: false       # 已生成的回答收不回来
  ceiling: D1.5
  blast_radius_cap: {gray: 0.05, calls_per_hour: 2000}
```

门禁读这份表决定本次变更能走到哪一档。**新增路径没有登记，则默认落到最严档并要求人工补登记**，这一条防止登记表被绕过：加一个新目录就能逃出分级，是这类机制最常见的失效方式。

`side_effects_reversible: false` 那一行是这份表存在的理由。**如果只按路径分级，提示词和文案会落进同一档**，因为它们的回滚动作一模一样。只有把副作用能不能撤销单独列出来，机器才分得清这两者。相应地，这一类必须带影响面上限，出问题时能限制住已经外溢的量。

下面按等级讲怎么一级一级往上走，以及每一级用什么工具。

## L1：人审的对象从代码换成契约

Berkeley 对第一级的描述是，AI 产出完整的 pull request，人以 pull request 粒度审查变更。这里要改一个字：**人审的不是代码，是契约。**

一个 Agent 一次产出四百行 diff，人读它要二十分钟，读完的判断质量还看当天状态。同样二十分钟花在审需求边界、异常路径、验收标准能不能机器检查上，产出的价值高一个数量级。代码质量可以由机器保证，需求边界不能。

下面按需求、架构、界面、计划、实现、测试、部署的顺序走一遍，每一步说清楚用什么、人在哪。

### 规约：用现成的，不要自己造

规约层用开源的 [agent-spec](https://github.com/ZhangHanDong/agent-spec)，不自研。

它把自己定义为意图编译器：意图（PRD、issue、对话）先编译成结构化需求作为中间表示，需求下降为可验证的任务契约，Agent 对着契约实现，机器验证代码是否满足契约。

```
意图（PRD · issue · 对话 · 探索发现）
      ↓  起草候选需求块，人评审接受
      ↓  需求治理门禁：proposed → accepted / rejected
knowledge/requirements/*.md      ← 需求条款，MUST / SHOULD / MAY
      ↓  需求语料 lint（含 EARS 与 ISO-29148 规范检查）
      ↓  依赖图校验
      ↓  下降为可执行或阻塞的工作单元
specs/*.spec.md                   ← 任务契约
      ↓  测试义务生成（从规约派生，与实现无关）
      ↓  Agent 在边界内实现
      ↓  lint → 结构检查 → 边界强制 → 绑定测试
      ↓  追溯：honored / violated / unproven
```

一份任务契约长这样：

```
spec: task
name: "离线笔记冲突合并"
satisfies: [REQ-SYNC-CONFLICT]
risk: A
---

## Intent
在客户端与服务端各实现一份行为等价的合并函数，
使同一条笔记在两台设备并发修改后，结果与到达顺序无关，且不丢失正文。

## Decisions
- 正文冲突不做自动截断或三方合并，保留两份并标记冲突
- 元数据按字段级最后写入优先，比较依据是记录自带的时间戳，不读系统时钟

## Boundaries

### Allowed Changes
- services/api/sync.py
- apps/mobile/lib/sync/merge.dart
- tests/sync/test_merge.py
- apps/mobile/test/sync/merge_test.dart

### Forbidden
- 不读取系统时间
- 不在合并中发起网络或数据库访问

## Completion Criteria

Scenario: 合并与到达顺序无关
  Test:
    Package: py
    Filter: tests/sync/test_merge.py::test_merge_is_commutative
    Level: property
    Targets: services/api/sync.py
  Given 任意一对笔记版本
  When 以两种顺序分别合并
  Then 两次结果相等
```

这份文件里有四样东西是 L1 的地基：

**第一，验收标准绑定到具体的测试函数。** 场景不是“应该正确合并”这种没法检查的话，是一个可以被执行的选择器。测试改名而契约没改，工具会报悬空选择器。

**第二，边界是硬约束。** 改动了 Allowed Changes 之外的文件，边界验证直接判失败。

在一个没有任何 Rust 代码的 Python 仓库里，改一个契约没声明的文件，工具直接报出来：

```
[FAIL] [boundaries] explicit change set respects declared paths
  x services/api/settings.py
    reason: not covered by any allowed boundary
```

边界验证只看路径，跟语言无关，零适配成本。 这是“Agent 改了不该改的东西”这类失效最便宜的拦截手段，建议第一天就上。

**第三，判定是五态而不是两态**：通过、失败、跳过、不确定、待复核，且明确规定跳过不等于通过。为什么必须是五态，后面讲执行器适配那节有个具体例子。

**第四，契约质量本身可以被 lint。** 上面那份契约跑一遍 lint，质量分 100%，但同时报出两条实质问题：有一条技术决策没有对应场景验证，五个场景全是正常路径没有异常路径。这两条恰恰是人评审时最容易漏的。 它直接支撑了 2.1 节那个定位：人审契约这件事，机器能帮上忙。

### 架构：不变量必须能被机器检查

架构这一层在 L1 阶段的分工很清楚：Agent 提方案，人批准决策；决策一旦落库，就变成机器强制的不变量。

Agent 提方案时强制给出两到三个候选，每个候选必须写明四件事：取舍、失败模式、迁移成本、**可逆性**。最后一项是这套方案特有的，因为撤销成本决定自主上限，那么一个架构决策会把某个模块推到哪一档等级，在选型时就该算清楚，而不是等上线之后才发现这块永远只能停在 D1。

人批准之后，决策记录进 `knowledge/decisions/`，从中抽出来的不变量进 `knowledge/standards/`。关键规定是：不变量必须写成能被静态检查的形式。

```
INV-001 客户端 MUST NOT 直接访问数据库          → Semgrep 规则
INV-002 Agent 编排层 MUST NOT 对外暴露端口      → 部署配置检查
INV-003 合并逻辑 MUST 是纯函数                  → Semgrep：禁用系统时钟调用
INV-004 用户数据出站 MUST 经过脱敏层            → Semgrep + OPA
INV-005 下发内容 MUST 只接受白名单组件          → 三方对齐脚本
```

**写不成检查的，说明它还停留在愿望阶段。** 要么细化到能写成规则，要么老实承认它只是一条指导原则，不要放进不变量清单里充数。一份混着“必须”和“最好”的不变量清单，等于没有不变量清单：Agent 分不清哪条是硬的，人也懒得逐条核对。

不变量还要再走一步，否则它进了 CI 但没进追溯体系：**把它们也写成需求条款**。

```
[REQ-INV-003] 合并逻辑 MUST 是纯函数，MUST NOT 读取系统时钟。
  Test:
    Package: semgrep
    Filter: rules/no-system-clock-in-merge.yaml
    Level: static
```

这样不变量和功能需求共用同一套三态追溯。少了这一步，某天有人把一条静态规则注释掉，需求追溯不会变红，架构约束就在无人察觉的情况下消失了。代价是执行器要多认一种静态检查，半天工作量。

触及不变量的变更一律走最高风险档，强制人审加双人批准。这条在任何等级下都不放松。

### 界面：设计产物必须进版本库

会话式设计工具（Claude Design 这一类）不适合做这一层的主力，原因不是能力，是**不可治理**：产出是一次会话的结果，不进仓库、不能 lint、不能 diff、不能在 CI 里回归。L1 尚可，到了 L2 它就是整条保证链上唯一说不清出处的环节。

三条准入标准：产出物是不是文件、能不能被机器校验、变更能不能被 diff。三条全过才能进。

本方案用一套交互设计技能 ixd-design（八阶段文档流，从苏格拉底式提问到可交互原型再到评审门禁），加上 Google 开源的 DESIGN.md 规范：

```
交互意图
  ↓ 一到三：产品上下文 → 信息架构 → 用户流程
  ↓ 四：逐页交互说明（布局、组件、行为、状态、动效、加载、适配、走查、微交互）
  ↓ 五加六：组件规范 + 视觉设计，合并输出为一份 DESIGN.md
  ↓ 七：可交互 HTML 原型      ↓ 八：交付文档 + 六角色评审门禁
```

DESIGN.md（`google-labs-code/design.md`）上半部分是 YAML 设计令牌给精确值，下半部分是散文说明为什么是这些值。它带命令行工具，设计系统因此第一次有了 CI 门禁：

```bash
npx -y @google/design.md lint docs/ixd/DESIGN.md              # 结构、引用、对比度
npx -y @google/design.md diff /tmp/base.md DESIGN.md          # 回归检测，退出码 1 阻断
npx -y @google/design.md export --format dtcg DESIGN.md > tokens.json
```

两处缺口要自研。一是导出的令牌格式到 Flutter 主题的转换器，用 Style Dictionary 加一个自定义格式器，约一人周。做完之后加一条静态规则：**Flutter 侧禁止任何硬编码样式值**，用 `custom_lint` 拦截裸颜色值与裸间距，这条消灭了 AI 生成 UI 最常见的不一致来源。

二是把逐页交互说明变成测试义务。第四阶段那份说明里有一节专讲状态流转（默认、加载、空数据、报错、无权限、离线、超长文本），这七种恰好是 AI 写 UI 时最常漏掉的。编译成契约场景后每种状态绑一个 golden 测试，它们就从文档变成了机器可检查的义务。桥接工具约两人周。

一点提醒：第八阶段那份 HTML 原型是**验收标准，不是要被翻译成 Flutter 代码的源**。两者布局模型不同，自动转换是死路。正确用法是页面规约、原型、golden 截图三方对照，不一致时优先怀疑实现。

### 计划与实现

现成的方法论技能包不少，superpowers 与 BMAD 最完整：前者流程链最全，从头脑风暴到收尾一应俱全，但**没有架构角色**；后者补上了架构角色，还带一个风险驱动的测试策略模块。

建议按技能挑，不要整包安装。两者重叠远大于互补，同时装会打架，同一个需求被问三遍。

更要紧的一条：**这些包里的门禁全部是提示词级的。** 不许没有设计就写代码、不许没有失败测试就写实现、不许没有新鲜证据就宣称完成，这些铁律都写在技能正文里靠模型自律。L1 有人在会话里盯着，所以有效；到了 L1.5 之后必须在编排层找到确定性的对应物，否则会静默失效。下一章有这张对照表。

方法论包之外，计划阶段基本是现成命令的组合：

```bash
agent-spec requirements work-units        # 需求下降为工作单元
agent-spec requirements plan --gate       # 需求 × 工作单元 × 契约三方对齐
agent-spec requirements test-obligations  # 测试义务，与实现无关
agent-spec requirements worktrees         # 并行 Agent 的工作树调度
```

加两条约束：单个契约的允许变更不超过八个文件，变更行数上限四百。L1 的保证机制建立在“人真的看得完契约”之上，超过这个量级人就开始扫而不是读，L1 悄悄变成假 L2。

实现阶段的分工，关键在上下文隔离：

| 角色 | 职责 | 可读范围 |
| --- | --- | --- |
| Implementer | 在边界内实现契约 | 契约、代码、只读规约服务 |
| Test Author | 从测试义务写测试 | **仅规约目录与测试目录** |
| Verifier | 独立评审契约完备性与实现一致性 | 全部，只读 |
| Explorer | 驱动模拟器探索 UI，只产结构化发现，不建 issue 不写文件 | 屏幕与日志，无仓库令牌 |

测试编写者的隔离用文件系统权限强制，不用提示词：它的工作目录只挂载规约与测试目录，物理上看不到实现代码。

这一条针对 Berkeley 点破的核心风险：同一个智能体既写实现又写测试时，测试通过证明的只是一致性，不是正确性。这类问题只能用权限解决。

### 测试：分层、编排、修复循环

| 层 | 内容 | 触发 | 阻断 |
| --- | --- | --- | --- |
| V0 规约 | 需求语料 lint、依赖图、计划一致性 | 每次推送 | 是 |
| V1 静态 | `flutter analyze`、`custom_lint`、ruff、mypy、架构不变量规则 | 每次推送 | 是 |
| V2 契约执行 | lint → 结构 → 边界 → 绑定测试 | 每次推送 | 是 |
| V3 接口契约 | 基于 OpenAPI 的有状态模糊测试、生成客户端联调 | 每次推送 | 是 |
| V4 端到端 | `integration_test` 回归 + Maestro 冒烟 + 真机矩阵 | 合并前 | 是 |
| V5 有效性 | 变异测试、Agent 行为评测、技能评测、需求追溯 | 每夜 | 报告 |

V5 最容易被跳过，代价也最高。它里面有两样东西别处替代不了。

变异测试回答“测试套件本身有没有用”：往实现里注入变异（改比较符、删条件分支），看测试会不会红。得分下滑意味着 Agent 在生产“通过但不检查任何东西”的测试，这是 L1 向上演进时的典型静默退化。关键模块下限设 80%。

需求追溯回答“意图有没有丢”：对每条需求重算三态，有契约且验证通过、验证失败、根本没有契约覆盖它。第三种最危险，意味着需求还在文档里但工程上已经没人管了。这个判定每次重算不落盘，所以不会出现“文档上写着已实现，但那是三个月前的事实”。

**谁来跑：四条工作流**

六层验证由四条 GitHub Actions 工作流承载，划分依据是触发时机与阻断力度，不是测试类型：

| 工作流 | 触发 | 内容 | 失败后果 |
| --- | --- | --- | --- |
| `spec-gate` | 每个 PR | V0：需求语料 lint、依赖图、计划一致性、契约边界 | 阻断合并 |
| `verify` | 每次推送 | V1 到 V3：静态、契约执行、接口契约 | 阻断合并 |
| `e2e` | 合并前 | V4：端到端回归、冒烟、真机矩阵 | 阻断合并 |
| `nightly` | 每夜 | V5：变异测试、需求追溯、行为评测、技能评测 | 出报告，不阻断 |

完整骨架见[工作流](#工作流一条完整的验证流水线)，执行器怎么把机械结果映射回契约见[退出码到五态的映射](#退出码到五态的映射)。

`nightly` 不阻断是刻意的：变异得分与行为评测都有噪声，**让有噪声的指标去阻断合并，最后一定会被加上跳过开关，然后所有人都忘了它的存在。** 正确做法是出报告加趋势告警，连续三天破线才登记问题。

**失败之后：自动测试与修复循环**

工作流负责发现，发现之后谁修是另一条循环：

```
CI 失败或夜间报告
   ↓ 分诊：是环境问题、偶发抖动，还是真实缺陷
   ↓ 真实缺陷 → 绑定到需求，生成或复用一份最小契约
   ↓ 隔离工作区里实施最小修复
   ↓ 回归有效性验证：修复前红、修复后绿、还原修复再变红
   ↓ 独立会话复核，默认拒绝
   ↓ 开 PR
```

这条循环本身不属于任何一个等级，它贯穿三级。 变的只有末端那道合并门由谁点头：

| 循环形态 | 末端动作 | 所处等级 | 开启条件 |
| --- | --- | --- | --- |
| 只读分诊 | 出报告，不建问题单 | L1 起步 | 零风险，第一个上线 |
| 发现循环 | 自动建问题单，附复现 | L1 | 误报率低于 30% |
| 修复循环 | 开 PR，人审后合并 | L1 | 契约体系已就位 |
| 修复循环加低风险自动合并 | R0 类直接合并，其余人审 | L1.5 | 风险分级策略上线 |
| 修复循环全自动 | 无人评审合并 | L2 | 影子运行一致性达标 |
| 自发起循环 | 自己提需求，再进上面的链 | L3 | 宪章与预算就位 |

先上只读分诊性价比最高：零风险、当天可上、不需要任何前置改造，而且能立刻回答一个关键问题，现有的 CI 失败里有多少是真缺陷、多少是环境抖动。这个比例决定后面每一步的可行性，一条循环如果一半时间在修抖动，产出的 PR 会迅速耗光人的信任。

### 部署：一键，加上失败自动回滚

L1 对应的发布等级是 D1。D1 不等于手工上机，它是“自动化到按钮为止”：

```
人点一次触发（deploy / restart / rollback，可指定版本）
   ↓ 环境保护 → 拉取版本 → 依赖同步 → 重启服务
   ↓ 探活（重试 + 超时）
   ↓ 失败 → 自动回滚到上次成功版本 → 再探活
   ↓ 成功 → 记录本次版本作为下次回滚锚点 → 结果通知
```

探活失败自动回滚是 D1 里唯一的自主动作，也是通往 D2 的第一块砖，必须在 L1 阶段就建好并演练过：后面所有等级的胆量都建立在“出事能回来”上。

**如果自动回滚本身不可靠，它比没有回滚更危险。** 两个常见缺口：回滚之后没有更新回滚锚点，下次回滚会错位；回滚时的依赖安装不卸载多余包，环境不是完全还原。启用任何合入侧自主之前先把它们修掉。

D1.5 只在一个地方成立：不重启进程就能生效、且能秒级撤销的变更，也就是前面那块人为造出来的地皮。这类变更走独立通道，经 schema 校验与组件白名单检查后自动放行，生效后监控前十分钟的崩溃率与关键漏斗，破线自动回退。它与二进制发布解耦，所以不需要人点按钮。

其余一切仍然是 D1。划分要写死在流水线里，一旦允许人临场判断这次该算哪一类，D1.5 会迅速蔓延到它不该覆盖的地方。

### 一处必须自己动手的适配层

除了界面那节的两处缺口，L1 还有一处必须自己动手：测试执行器的适配。agent-spec 当前的执行器绑定 Rust 工具链，Python 与 Dart 项目需要外接。做法是用契约里的 `Package` 字段作判别式（`py` 走 pytest，`dart` 走 `flutter test`，再加一个静态检查分支让不变量也能被契约绑定），把结果按五态映射回去，实现约三天。

这里能看出五态的价值。工具链缺失时判不确定而不是失败，因为**无法求证不等于被证伪**；两态模型只能在过和不过里二选一，一定会把环境问题记成质量问题。退出码到五态的完整映射，以及几个容易写错的地方，见[退出码到五态的映射](#退出码到五态的映射)。

### 什么时候算达标

六条硬指标，连续窗口内全部达标才允许提升：

| 指标 | 阈值 | 窗口 |
| --- | --- | --- |
| unproven 需求占比 | ≤ 5% | 4 周 |
| violated 事件 | 0 | 4 周 |
| 变异得分（关键模块） | ≥ 80% | 4 周 |
| 属性级场景占比（关键模块） | ≥ 30% | 达标即可 |
| **人审拦截率**（人审独有发现占比） | **≤ 15%** | 8 周 |
| 部署回滚演练 | 各服务各成功 1 次 | 已完成 |

**人审拦截率是这六条里的核心。** 它的含义是：人审能发现的问题里，有多大比例是自动化发现不了的。如果这个数字降到 15% 以下，说明去掉人审的边际损失可控；如果它常年居高不下，说明验证层还不够，硬升级就是 Berkeley 文章里说的“跳级”。

属性级场景占比那一条，用前面那份合并契约就能说明。把实现改坏（排序改成按到达顺序拼接，破坏交换律），“两份内容都保留”这个例子级场景照样通过，只有“与到达顺序无关”这个属性级场景会红。契约里的场景类型分布，直接决定它能拦住哪类失效。 全是正常路径的契约，对交换律、幂等性、无丢失这类性质完全是盲的。

## L1.5：给悬崖搭一级台阶

### 为什么必须有这一级

L1 是每个契约都人审，L2 是完全不审。中间没有台阶。

用关卡视角说，L1.5 **不是移除关卡，是把关卡概率化**：那道门还在，但只对一部分变更落下来。

这中间的落差有多大？Berkeley 的文章里点得很准：眼下最紧迫的风险不是什么花哨的完全自主系统，而是组织跳级。一个团队名义上在第一级运行，实际上智能体生成的改动合并进去了却没人真正仔细检查过。

**这件事不会因为你写了规范就不发生，它会因为疲劳而发生。** 唯一的对策是把“不审”变成一个显式的、有比例、有记录、有回归数据的工程决策。

### 风险分级用策略表达

分四级：

- **R0** 可逆低影响（文案、样式、测试补充）：自动合并
- **R1** 常规功能变更：抽检 20%
- **R2** 同步协议、认证、计费、数据迁移：强制人审
- **R3** 架构不变量、安全边界、CI 配置、技能定义：强制人审加双人批准

分级判断可以让技能来做，**但门禁必须是确定性的**。用声明式策略而不是脚本：路径规则、悬空测试选择器、契约边界越界，三类判定各写成一条规则，完整策略见[门禁怎么写](#门禁怎么写)。

一段 Rego 是可读的规则集，一段脚本是一个需要自己写测试的程序。**门禁写成策略而不是代码，是为了让它能被评审。**

R3 那三条路径值得单独强调：CI 配置、技能定义、架构不变量。**一个能修改自己门禁配置的 Agent，等于没有门禁。** 这一条在任何等级下都不放松。

这一级的出口准则很短：R0 类变更的自主合并率不低于 90%，逃逸缺陷密度不上升，连续 8 周；审计包完备率 100%。

### 审计包：从审查制品到审计过程

Berkeley 的一条预测是保证工作从审查代码转向认证智能体。落到工程上，就是每次自主变更归档一份审计包，里面有执行轨迹、五态判定与覆盖矩阵、AI 物料清单、设计系统校验、评测结果、变异得分、不可抵赖的制品证明。

原则是只收集不生产，全部用现成标准。其中 AI 物料清单不要自己发明格式：CycloneDX 已经有 AI-BOM 标准，工具链已经支持把模型元数据、提示词文件、工具配置作为组件纳入清单。自造格式的结果是没人能消费它，**包括未来的审计方**。

有了这份清单，当某个模型版本或某条提示词后来被发现有系统性缺陷时，能立刻查出它生产过哪些代码。没有它，一旦发现问题就无法定位影响面。

保留期限：R2 以上永久，R1 两年，R0 六个月。轨迹里的内容一律外置只存引用，脱敏在采集侧兜底，这样密钥与敏感数据的处置面收窄到一个地方。

### 落地现状（kite 验证，2026-08-08）

L1.5 三件在 kite 全部落地并 CI 真跑验证，下面是实际接线与几个理论没点明的坑。

**风险分级接线**：`policy/risk.rego`（R0-R3 + deny）+ `spec-runner risk` 子命令（subprocess `opa eval`；opa 缺失 exit 2、deny 非空 exit 1）。input 三类全填：
- `changed_files/lines`：用 `origin/main...HEAD`，**不用 `git diff HEAD`**——CI 里 `flutter pub get` 会重生成 `pubspec.lock`，工作区副作用会污染分级；只看 committed PR 改动才准
- `boundary_violations`：扫所有 specs 的 `allowed_changes` 并集 + 白名单（元文件/文档/配置这些不需契约覆盖的自由区）vs changed
- `dangling_selectors`：scenario 的 test selector 文件不存在、或 py 函数不存在（查 `def test_func`）

**R0 自动合并**：repo 开 `allow_auto_merge` + main branch protection（require PR + status check + `enforce_admins=false` 保留 owner 紧急绕过）。verify.yml 的 contract job 输出 risk level，`auto-merge` job：R0 → `gh pr merge --auto --squash` / 非 R0 → PR comment。**PR #3（docs 小改）真自动 MERGED 验证通过**。

**审计包**：`spec-runner audit-seal` → `.out/audit/<commit>.json`。CycloneDX 1.5 AI-BOM（`sherpa_onnx` 版本从 pubspec 动态提），制品只存引用（evidence/risk/shadow/design/eval/mutation，不复制内容），`retention` 按 level（R2+永久/R1两年/R0六月），`--archive` 入库 `audit-seal/`。影子记录追加 `.out/shadow.jsonl`，为 L1→L1.5 切换准入（一致性 ≥90%）攒数据。

**关键叡坑（CI 真跑才暴露）**：branch protection 的 `required_status_checks.contexts` 要匹配 check run name（是 `contract` 不是 `verify / contract`）；auto-merge job 没 checkout → `gh pr merge --repo` 免 checkout；非 R0 用 `gh pr comment` 而非 `--add-label`（label 要预建 + 权限碎）。

## L2：人不看代码之后，什么顶上来

### 行业边界在哪

进入这一章之前有个事实值得摆出来：**截至 2026 年年中，主流的编码代理全部停在合并这道门前。**

Copilot、Devin、Claude Code、Sentry 的归因代理、Datadog 的基础设施代理，覆盖的环节已经包括规划、编码、测试、开 PR、回应评审意见，输出一律经人工批准才能进生产。Datadog 那边的原话是代理提 PR，工程师决定合什么。

例外只有一个方向：有工具开始对低风险 PR（文档更新、单元测试、简单缺陷修复）直接给出批准而不上报给人。**这恰好就是上一章的 L1.5，它已经是可以买到的产品形态。**

**L2 没有现成产品，D 轴更是完全空白。** 这解释了后面为什么有那么多东西要自己做，不是不想用现成的。

### 从提示词到退出码

L1 到 L2 的实质变化，用一句话说是：**同一批约束从提示词搬到了退出码里。**

上一章提到的方法论技能包，它们的铁律全部靠模型自律执行。L1 阶段这样没问题，因为有人在会话里盯着；L2 没有人盯，每一条都必须找到确定性的替身：

| 提示词级的铁律 | L1.5 之后的确定性替身 |
| --- | --- |
| 没有设计批准不许写代码 | 契约未进版本库则工作流不启动 |
| 没有失败的测试不许写实现 | 回归有效性验证的第一段：修复前必须红 |
| 没有新鲜证据不许宣称完成 | 五态判定的退出码 |
| 每个任务必须评审 | 契约执行加边界强制 |
| 子代理不继承会话上下文 | 文件系统权限 |

这张表是 L2 的实质定义。 不是加了什么新能力，是把同一批约束从会不会被上下文冲淡的地方，搬到了会不会返回非零退出码的地方。

### 先划定不做什么

**必须永久留在 L1 的**：认证与授权、计费与配额、数据迁移脚本、加密与密钥处理、服务端下发内容的渲染器与表达式求值。

**可以进入 L2 的**：常规业务接口与数据模型扩展、Agent 的工具实现与提示词优化、页面编排与文案、实验配置、内部工具与运维脚本、测试补充与重构。

**用最低风险模块的成功，论证最高风险模块的安全性，这个推理本身就是错的。**

还有一处不对称必须说明白：客户端侧的合入等级上限比服务端低，不只是因为商店审核。 服务端有确定性探索引擎（下面第三根柱子），客户端没有等价物。客户端的 golden 测试与布局断点是回归不是探索，探索完全靠 Explorer 与视觉初筛这两个概率性角色。这个验证能力的不对称，才是客户端停在 L1.5 的真正原因。

### 人退到需求那道门之后，看什么

有一处措辞要精确：L2 下人介入的是需求的**接受**，不是需求的**提出**。

人仍然给高层意图，Agent 把它扩展成完整需求条款。人在这道门上做的不是判断需求写得好不好，而是**判断哪几条是 Agent 猜出来的**。

所以扩展结果必须把来源标出来：

```yaml
provenance:
  stated:   ["支持多设备冲突提示"]              # 人说的
  inferred:
    - text: "提示样式沿用已有的轻提示组件"        # 高置信
    - text: "冲突保留两份而非覆盖"                # 中置信
    - text: "提示七天后自动清理"                  # 低置信
```

低置信度的推断自动升级为人审。**守护意图最实际的手段不是让人审所有东西，是让机器主动标出“我这里是在猜”。** 这道门的价值全在这一点上，去掉标注，人就退化成了橡皮图章。

### 四根柱子

L1 的保证结构是“自动化验证 + 人审兜底”。去掉人审之后，必须补上四根柱子。

**柱一，确定性门禁承担主要判定。**

L2 下九成的判定由不调用模型的命令做出：需求语料 lint、依赖图校验、计划一致性、契约执行、需求追溯、策略门禁。

顺序不能反。先让确定性门禁筛掉能筛的，概率性的裁决只处理剩下的不确定项。反过来做，模型会在大量本可机械判定的事情上浪费判断力。

**柱二，反自洽验证链。**

Berkeley 点破的核心风险是“自洽但不正确”：写测试的智能体产出的实现和测试套件彼此一致，但两者一起错了。

对策是六层叠加，注意它们的性质：

| 层 | 手段 | 拦截 | 性质 |
| --- | --- | --- | --- |
| 1 | 测试从规约派生，与实现无关 | 测试继承实现的错误假设 | 确定性 |
| 2 | Test Author 上下文物理隔离 | 测试照着实现写 | 确定性 |
| 3 | **回归有效性验证** | 修复没对症、测试形同虚设 | **确定性** |
| 4 | 变异测试打分 | 测试套件整体无效 | 确定性 |
| 5 | Verifier 五项检查 | 附带损害、越界 | 概率性 |
| 6 | 独立裁决：不假设契约正确，独立推演后再对比 | **契约本身错了** | 概率性 |

第三层是整条链里最省钱的一环。 它的规则是三段：修复之前，相关测试必须是红的；修复之后，必须变绿；**把修复还原掉，必须再变红。**

第三段是关键。前两段只证明了“改了之后测试过了”，第三段证明了“这个测试确实在检验这个修复”。而后者正是“自洽但不正确”伪装得最像的地方。它的代价只是两次额外的机械执行，没有任何模型调用。

第六层是唯一能发现契约本身有洞的层，前五层都以契约为真。它只需要在不确定项与高风险变更上跑，提示词里要写明：不要假设契约是对的，先独立推演这个需求的合理行为，再与契约对比。

还有一个便宜的补充手段叫**分歧检测**：让实现者和测试编写者在动手之前各自写下自己理解的验收条件，由第三方比对。两份理解不一致，说明契约有歧义，此时不是让某一方让步，而是回到需求澄清阶段消歧并升级人审。

**柱三，确定性探索引擎。**

L2 下人不再看代码，也就不再有人凭直觉“这里可能有问题”。这份直觉必须有东西接替。

分工原则是：**界面语义模糊，只有 Agent 能理解，所以 UI 侧的探索由 Agent 驱动；协议行为完全成文、可观测性极好，所以后端的探索由确定性引擎驱动。**

后端四种引擎，全部零 token：

| 引擎 | 手段 | 捕获 |
| --- | --- | --- |
| 属性与状态机 | Hypothesis 的状态机测试，自动生成乱序、非法、边界的报文序列 | 挂死、不变量破坏，失败自动收缩到最小复现序列 |
| 模糊测试 | 对编解码器与解析器做随机输入 | 崩溃、未捕获异常 |
| 差分测试 | 同一序列打两个行为应当等价的服务，比对响应与副作用 | 双份实现之间的漂移 |
| 混沌演练 | 多角色蜂群 + 故障注入，结束后检查全局不变量 | 并发、时序、连接泄漏、补推竞态 |

举个典型缺陷。两个后端服务共用一套离线通知存储，各自默认写同一个库位，对同一用户的通知会互相覆盖。两边代码单看都对，代码评审几乎不可能发现，但差分测试立刻抓到：同一序列打两个服务，结果不一致。

接法同样要紧：把每一条不变量写成需求条款，让引擎成为它的验证手段。

```
[REQ-PROTO-POISON] 非法包或乱序包 MUST NOT 导致连接挂死或影响其他会话。
[REQ-NOTIFY-ISOLATION] 两服务的离线通知存储 MUST NOT 互相覆盖。
```

这样引擎跑一夜就不只是“测试没红”，而是“这几条需求今晚仍然成立”。

**柱四，发布侧不能替合入侧兜底。**

这是一根反面的柱子：L2 下不能指望“发上去看看”。撤销成本高的系统里发布侧只有 D1，没有金丝雀、没有指标自动回滚，合入侧那三根必须自己站住。

如果你的系统撤销成本足够低（无状态、多副本、秒级回滚），渐进发布可以补上这一根，此时记得加一条常被忽略的回滚条件：**单请求推理成本**。Agent 后端有一类特有失效是功能正确、延迟正常，但推理成本翻了三倍。

### 一条贯穿全篇的阶梯

遇到一类失效，按这个顺序找解法，能用左边的绝不用右边的：

```
契约边界强制  >  静态规则  >  确定性引擎  >  策略门禁  >  技能（提示词）
```

越靠左越确定、越便宜、越不会自己出错。举几个实例：

| 失效 | 错误做法 | 正确做法 | 位置 |
| --- | --- | --- | --- |
| Agent 改了不该改的文件 | 写技能说明禁改 | 契约 Forbidden 段，边界验证硬拦 | 1 |
| Agent 硬编码颜色值 | 写技能强调用令牌 | `custom_lint` 规则 | 2 |
| 设计令牌与代码主题漂移 | 人工 review | 导出后 diff | 2 |
| 两个服务的共享状态互相覆盖 | 代码评审 | 差分测试 | 3 |
| 乱序报文导致连接挂死 | 补几个用例 | 属性状态机遍历 | 3 |
| 改了测试名不改契约 | 写技能提醒 | 策略检测悬空选择器 | 4 |
| 需求模糊时 Agent 自行编造 | 只能用技能 | 意图编译技能 + 澄清提示 | 5 |

**只有最后一类真的需要技能。技能是用来处理判断的，不是用来处理规则的。**

这条阶梯还有一个推论：技能本身也要有 CI。 提示词会退化，退化了没人知道，模型版本升级还会静默改变它的行为。每次修改技能跑评测对比基线，回归则阻断；每月全量回归一次。技能版本进 AI 物料清单。

### 什么时候算达标

| 指标 | 阈值 | 窗口 |
| --- | --- | --- |
| 自主合并率（L2 范围内） | ≥ 70% 且稳定 | 12 周 |
| 逃逸缺陷密度 | ≤ L1 水平 | 12 周 |
| violated 事件 | ≤ 1 次/月且 24 小时内闭环 | 12 周 |
| 跳过与待复核未闭合数 | 0 | 12 周 |
| 回归有效性验证通过率 | ≥ 95% | 12 周 |
| **Verifier 拒绝率** | **稳定在 10% 到 25%** | 12 周 |

**Verifier 拒绝率有下限不是笔误。** 常年低于 10% 说明它在盲签，此时必须注入人工构造的缺陷做校准测试。一个从不说不的验证者，等于没有验证者。

---

### 落地现状（kite L2-1，2026-08-08）

L2 是长期目标（12 周达标窗口），kite 刚起步。已建第一根柱子的一层：

**柱二·层 3 回归有效性验证**：`spec-runner regression-check <spec>`。假设工作区含修复（git diff），`stash` 还原跑测试（期望红）→ `pop` 恢复跑（期望绿）。`before=FAIL + after=PASS` 才有效——`before=PASS` 说明测试没测这个 bug（自洽但不正确），退 1。零模型调用，两次机械执行。

**柱二·层 4 变异测试**：`pyproject [tool.mutmut]` + nightly.yml 接线（`mutmut run/results`，不阻断走趋势，`workflow_dispatch` 手动触发）。变异得分是 L2 达标观测（关键模块 ≥80%）。

**provenance（需求接受）**：`spec-runner provenance-lint` 检查 requirement 的 Source Trace + stated，收集低/中置信 inferred 升人审。落地即抓到 kite 4 个 requirement 缺 stated（格式漏 `stated:` 前缀），已修。

主要给 Agent 修复任务的会话内验证（修完跑一遍再 commit）。CI 接线（commit-ref 模式，HEAD vs HEAD~1）留后续——PR 工作区干净，stash 无效。

**柱三 确定性探索**：kite 属性测试已遍布（proto/classify/search/transcribe/queue/isolation/sync 全有 hypothesis `@given`，proto 防毒已是流遍历探索），spec 绑定不变量（task-proto-poison 等）。nightly 加长探索（`HYPOTHESIS_MAX_EXAMPLES=1000`，CI 默认 100），过夜抓白天漏的。状态机/差分/混沌按场景后续。

**待建**：柱二其余层（Test Author 隔离、Verifier 五项、独立裁决）/ 柱三状态机·差分·混沌 / 影子运行达标（L1.5→L2 切换准入）。

## L3：只做试点，范围极窄

### 循环半径决定了你必须配什么

关卡越靠外，循环半径越大，一圈跑完的时间越长，**错误被发现的延迟也越长**：

| 等级 | 错误多久暴露 | 因此必须配什么 |
| --- | --- | --- |
| L1 | 分钟到小时，PR 上就拦下了 | 契约评审即可 |
| L2 | 天，要等需求验收或线上指标 | 逃逸缺陷追踪、影子运行 |
| L3 | 月，单次变更都合规，问题出在累积 | 月度累积效应审计 |

这张表解释了 L3 那条月度审计为什么不是谨慎，是必需：**L3 的自然反馈周期就是月级，不配一个月级的检测手段，等于在这一级上没有反馈。**

记忆需求同样跟着半径长：L1 的循环可能一次会话内跑完，L2 跨会话跨天需要落盘的状态与运行账本，L3 跨月需要长期趋势与黄金旅程的前后对比。**半径决定了你必须记住多久的事。**

### 允许与禁止

Berkeley 对第三级的描述是：AI 从遥测、用户行为、安全公告、依赖变更中识别需求，人在循环开发中的最终角色消失。核心挑战变成如何确保 AI 自己产生的需求始终服务于人设定的使命，而不是悄悄重新定义它。

本方案对第三级的处置是：**建立机制、小范围试点、不做全面推广。**

机制必须在 L1 阶段就建好，不能等 L2 跑顺了再补。宪章、变更预算这类约束一旦晚于流程成型，就长不进去了。

**允许 L3 的范围**：依赖升级与安全补丁（有明确触发、目标清晰、可逆）、崩溃与错误的自愈修复（有明确失败信号）、性能与成本优化（有量化目标、行为不变）、测试覆盖补充（纯增量）、文案与本地化、内部工具与运维脚本。

**禁止的范围**：任何面向用户的新功能、任何涉及数据模型与权限与计费的变更、任何改变产品定位或交互范式的变更、任何修改使命宪章与架构不变量的变更。

还有一条要单独写出来：**L3 与发布自主完全解耦。Agent 可以提需求，但永远不能决定什么时候上线。**

### 使命宪章

宪章是整个体系的锚：由人撰写，Agent 只读，需两名人类批准，提交需签名，每季度复审。

```markdown
# Kite 使命宪章 v1

## 存在目的
帮助用户以最低的心智负担捕捉、组织、找回自己的想法。

## 不可违背的约束
1. 用户数据属于用户。任何默认行为不得扩大数据出站范围。
2. 不以增加使用时长为优化目标。
3. 离线可用性优先于新功能。
4. 任何 AI 生成内容必须可追溯到来源，不得以确定语气陈述不确定信息。
5. 不引入以留存为目的的通知策略。

## 明确的非目标
- 不做社交、不做内容分发
```

第 2 条和第 5 条是刻意写的。 它们防的正是 Berkeley 说的奖励黑客：如果 Agent 的优化目标里有留存或时长，它迟早会自己发明推送策略。宪章必须提前把这类代理指标堵死。

### 需求候选管线

```
遥测（崩溃 · 漏斗流失 · 工具失败率 · 成本异常）
外部（依赖公告 · 上游接口弃用 · 平台政策 · 应用商店评论）
      ↓ ① 净化：外部文本只允许转成枚举字段，原文不进下游提示词
      ↓ ② 聚类归因
      ↓ ③ 提案生成：预期收益、成本估算、风险等级、可逆性
      ↓ ④ 宪章一致性逐条论证
      ↓ ⑤ 预算闸门
      ↓ ⑥ 人抽检 ≥ 20%，全量事后可审
      ↓ 进入 L2 流水线执行
```

第一步是安全关键，不能省。用户反馈、商店评论、上游公告都是不可信输入，直接拼进提示词等于开放了一条从外部到自主变更的注入通道。Berkeley 的文章专门点了这个风险。

由此有一条可推广的原则：**处理不可信内容的角色不持任何仓库令牌、无文件写工具、只产结构化输出，落盘与建单由可信编排代码执行，带路径白名单、复现校验、指纹去重。** 敏感字段的检测正则同理，硬编码在编排代码里。安全约束写进提示词就会被上下文冲淡，也会被注入绕过。

第四步的宪章一致性判定是全方案里少数必须用模型判断的地方，所以它必须配评测集，用人工构造的越界提案做校准。

### 变更预算

L3 最危险的失效不是某一次改错，而是持续的、每次都合理的小改动累积成方向漂移。

| 预算项 | 周期上限 |
| --- | --- |
| 自主发起的需求候选 | 10 条/周 |
| 累计变更行数 | 3000 行/周 |
| 推理成本 | 按月硬预算 |
| **单模块连续自主变更** | **3 次/月** |

最后一条对抗的是 Agent 的折腾倾向：在同一处反复微调，每次都有理由，整体没有净收益。

再加一个月度审计，由独立 Agent 执行输出给人：本月所有自主变更的意图摘要、与宪章各条的对照、固定黄金旅程的前后行为 diff，以及累积效应分析。

最后一项是关键。单看每个变更都合规，合起来可能已经把产品推向了另一个形态。这个检测只能定期整体做，无法在单次变更时完成。

## 什么该自研，什么不该

### 动手之前先问四个问题

自主开发这个题目最容易失控的地方，是把每一个缺口都变成一个自研工具。一份没有节制的清单很容易膨胀到三十几人周，而其中大部分能力早就有人做过了。

动手写工具之前，按顺序问四个问题：

1. **规约工具的命令表里有没有？**（需求、追溯、边界、计划、审计）
2. **是不是某个标准的一部分？**（DESIGN.md、W3C 设计令牌、OpenTelemetry GenAI、CycloneDX、OpenFeature）
3. **能不能用声明式策略表达？**（Rego 而不是代码）
4. **是不是只是把上面几样串起来？**（那是一个五十行脚本，不是一个工具）

四问都否，才动手。大部分看起来需要自研的能力，在第一问或第二问就该停下。

### 看起来要自研，其实不用

规约层与设计层的替代方案前面已经讲过（agent-spec 与 DESIGN.md）。除此之外，还有五处容易误判：

| 能力 | 不该自研的理由 | 用什么 |
| --- | --- | --- |
| 门禁路由器 | 门禁应当是可评审的规则集，不是程序 | OPA 策略 + 契约边界 |
| 智能体审计器 | 轨迹、清单、证明三样都有标准 | OpenTelemetry GenAI + cdxgen + 制品证明 |
| 评测框架 | 引擎不需要自己写，只需要 CI 封装 | promptfoo 或 Inspect AI |
| 成本核算器 | 令牌用量已是标准指标，网关自带预算 | LiteLLM + OpenTelemetry |
| 遥测到需求的挖掘器 | 全量做太重，只保留净化与提案两件事 | 分类模型 + 薄脚本 |
| 整套开发方法论 | 现成的技能包流程比自己写的完整得多 | superpowers 或 BMAD，**按技能挑，不整包装** |

自研合计约 8 到 10 人周。克制自研清单省下来的工程量不会消失，它转移到了更该花力气的地方：把这些工具编织成一套会自我进化的技能库，以及为每一级建立可测量的出口准则。

每一级具体新增哪些文件，见[每一级新增什么](#每一级新增什么)。

## 这套东西什么时候不该上

**不该上的情形一：项目还没有稳定的测试基座。** 整套体系的第一性前提是“测试即验证器”。没有测试就没有闭环，Agent 修完了没有任何东西能判断它修对了。先补测试，再谈自主。

**不该上的情形二：密钥还在仓库里。** 给 Agent 仓库读写权限之前，明文凭证必须出库并轮换。Agent 会读到它们，并可能在 issue 或 PR 中扩散。这是一个绝对的前置条件，不是“顺便做一下”。

**不该上的情形三：变更量不足以摊平成本。** 这套体系的固定成本是实打实的：8 到 10 人周的工具建设，加上持续的技能迭代。如果一个项目每周只有两三个变更，人工做完全更划算。

停止条件也要写下来：若单需求总成本连续两个月高于人工基线，且逃逸缺陷密度没有下降，就降级并复盘。没有停止条件的技术改造，最后都会变成沉没成本的俘虏。

还有三个信号，出现任何一个就要停下来查：

- Verifier 长期不说不 → 验证层已经失效，只是看起来一切正常
- unproven 需求比例上升 → 需求正在脱管，规约与实现在分家
- 重试成本占比超过三成 → 问题出在契约质量，不是模型能力，换更贵的模型解决不了

## 第一部分小结：三样稀缺的东西

Berkeley 那篇文章的最后一条预测是：软件变得充裕，信任变得稀缺。落到工程上，稀缺的是三样东西。

**可追溯的意图**，哪条需求要求了这个行为。链条是需求条款到契约到代码注解到测试选择器，断在哪一环，哪一环就是意图丢失的位置。

**可复现的证据**，这个判定怎么得出的、能不能再跑一遍。确定性门禁与红绿红三段提供这一样，概率性的裁决只是补充。

**可撤销的动作**，出事之后多久能回到上一个已知良好状态。它决定了前两样能换来多少自主权。

把 Berkeley 的一个轴拆成两个，原因就在第三样：合入侧可以走得很远，因为撤销一个提交的代价接近于零；发布侧走不远，因为打断一场正在进行的会话无法撤销。分开定级不是保守，是把风险放在它真正所在的位置。

至于 L1 到 L3，它不是要奔赴的目的地，是这套体系成熟度的读数。等到某一类失效再也不出现，那一级自然就到了。

## 仓库长什么样

先把上篇散落在各章的路径汇总成一棵树。样板产品仍然是 Kite，一个个人 AI 助理，客户端 Flutter 双端，后端 Python 分成 Agent 编排层与 API Server。

kite/

**三条摆放原则**，比目录本身重要：

能入库的一律入库。 契约、策略、登记表、指纹、技能、评测样本，全部是文本文件走版本控制。入库的东西才能被评审、被 diff、被回滚。任何存在数据库里而没有对应文件的规则，都是无法评审的规则。

规则与它的检查手段放在一起。 `knowledge/invariants/` 里的条款直接指向 `rules/` 里的规则文件，两者一起改、一起评审。分开放的结果是规则被改了而条款还在。

跨运行的可变状态单独放 `state/`，并且尽量少。 每多一样跨运行状态，就多一份“谁改的、什么时候改的”说不清的东西。见[状态存在哪](#状态存在哪)。

## 技能、编排、工作流各给一份样本

上篇说载体是技能、编排、工作流三层，三层的失效后果分别是质量下降、越界、失控。这里各给一份能照抄的样本。

### 技能：一份完整的 SKILL.md

以隔离测试编写者为例，它是反自洽链条的第二层。完整内容见仓库 `.claude/skills/test-author/SKILL.md`。

最后两行（落盘与提交由编排层执行）是这份技能真正的约束所在。 但注意，它写在提示词里只是说明，实际强制在下一层。

### 编排层：唯一提供确定性的地方

**以下是参考实现**，接口按你自己的编排框架调整，形状比签名重要。完整代码见仓库 `tools/orchestrator/`。

三条设计要点：

权限来自配置文件，不来自提示词。 技能里写“你看不到实现代码”是说明，`allowedTools` 与工作目录挂载才是强制。

用量直读，不靠模型自报。 让模型报告自己花了多少令牌，等于让它给自己记账。

预算检查在调用之前。 耗尽了直接抛异常，不要进了模型再判断，否则超支的那一次已经花掉了。

落盘同理，永远由编排代码执行，带白名单校验。路径越界检查里那个 `base + '/'` 不能省。 只判前缀的话，`tests-evil/` 会被当成 `tests/` 的子路径放行。这是这类白名单最常见的写法错误。

### 工作流：一条完整的验证流水线

完整骨架见仓库 `.github/workflows/verify.yml`。

倒数第二步的顺序不能调。 先跑确定性门禁，再算风险分级。反过来的话，一个高风险变更会因为分级通过而跳过本该阻断它的契约检查。

第三方 action 一律锁提交哈希，不锁标签。标签可以被重新指向。

## 契约怎么绑定测试

### 用 Package 字段分派

契约里的测试选择器是结构化字段，`Package` 直接当作执行器判别式：

```
Scenario: 合并与到达顺序无关
  Test:
    Package: py                                    # py | dart | semgrep
    Filter: tests/sync/test_merge.py::test_merge_is_commutative
    Level: property
    Targets: services/api/sync.py
```

执行器注册表：

```python
# tools/spec-runner/spec_runner/adapters/__init__.py
from . import pytest_adapter, flutter_adapter, semgrep_adapter

ADAPTERS = {
    "py": pytest_adapter,
    "dart": flutter_adapter,
    "semgrep": semgrep_adapter,     # 让不变量也能被契约绑定
}
```

第三个适配器是[架构那节](#架构不变量必须能被机器检查)说的不变量追溯的落点。加了它之后，`REQ-INV-*` 与功能需求共用同一套三态追溯，静态规则被注释掉会让需求变红。

### 退出码到五态的映射

这张表是整个执行器最容易写错的地方，因为退出码的语义比文档写的模糊。

| 执行器 | 情况 | 判定 | 理由 |
| --- | --- | --- | --- |
| pytest | 退出 0，收集数大于 0 | pass | |
| pytest | 退出 0，收集数为 0 | **fail** | 选择器命中零个测试，契约缺陷 |
| pytest | 退出 1 | fail | 有测试失败 |
| pytest | 退出 5 | **fail** | 未收集到测试，同上 |
| pytest | 退出 4 且输出含未找到标记 | **fail** | 悬空选择器 |
| pytest | 退出 4 其余情况 | uncertain | 用法错误，工具链问题 |
| pytest | 退出 2 或 3 | uncertain | 中断或内部错误 |
| flutter | 事件流中可见测试数为 0 | **fail** | 同上，注意排除框架自动生成的隐藏用例 |
| flutter | 有测试结果非成功 | fail | |
| flutter | 命令不存在 | uncertain | 工具链缺失，不等于被证伪 |
| semgrep | 退出 0 | pass | 无发现 |
| semgrep | 退出 1 | fail | 有发现，即违反不变量 |
| semgrep | 退出 2 | uncertain | 规则文件错误 |

两条容易踩的：

**pytest 对不存在的测试名返回 4，和真正的用法错误共用同一个退出码。** 缺失的测试文件也是 4。只看退出码会把“测试被删了”这个契约缺陷伪装成“环境有问题”，于是 CI 表现为间歇性红灯，团队很快开始无视它。必须再看输出里有没有未找到的标记。

**Flutter 的机器可读输出里有隐藏用例。** 框架会为每个测试文件生成一条加载用例并标记为隐藏，不排除掉的话，一个命中零个真实测试的选择器会被判成通过。

判定的序列化也有坑：待复核这个状态在常见实现里序列化成全小写无下划线的形式，写成带下划线会被静默忽略。

### 五态怎么处置

```python
# tools/spec-runner/spec_runner/gate.py
DENY_ALWAYS = {"skip", "pendingreview"}

def gate(results, level):
    problems = []
    for r in results:
        v = r["verdict"]
        if v == "fail":
            problems.append(f"[fail] {r['scenario']}: {r['reason']}")
        elif v in DENY_ALWAYS:
            problems.append(f"[{v}] {r['scenario']}: 跳过不等于通过")
        elif v == "uncertain":
            if level in ("L2", "L3"):
                problems.append(f"[uncertain] {r['scenario']}: 无人兜底，升级人审")
            else:
                problems.append(f"[uncertain→人审] {r['scenario']}: {r['reason']}")
    return (not problems), problems
```

跳过永远阻断，这一条不设开关。 一旦提供了跳过开关，它会在某个赶工的周五被打开，然后再也不会被关掉。

## 角色隔离靠权限，不靠叮嘱

反自洽链条的第二层靠 `.claude/agents.json` 强制，不靠提示词。完整配置见仓库。

三点说明：

测试编写者的 `deny_read` 比 `read` 更重要。 只给读列表是不够的，因为很多工具会通过间接路径读到文件。显式拒绝加上工作目录隔离才靠得住。稳妥的做法是给它一个独立的 worktree，里面根本没有实现目录。

验证者只读。 它一旦能改代码，就会倾向于“我顺手修一下”，独立性当场消失。

`locked: true` 是验证者专属。 含义是它的模型档位不允许被任何环境变量或网关降级，检测到降级即停机。验证者放行的错误不可回收，这是唯一不能省成本的角色。

## 红绿红三段怎么跑

上篇说这是整条反自洽链里最省钱的一环：修复前必须红、修复后必须绿、**还原修复必须再红**。第三段是它区别于普通 CI 的地方。

**以下是参考实现**，用独立工作树而不是暂存区，避免污染当前工作区。完整脚本见仓库 `tools/orchestrator/repro-gate.sh`。

注意只还原实现路径，不还原测试路径。 这是全脚本的关键：两者一起还原的话，测试也回到了修复前的版本，第一段必然红，但那证明不了任何事情。`--only-impl` 从契约的允许变更列表里滤掉测试目录。

第一段和第三段看起来重复，实际不是：中间夹着一次绿，三段连起来才排除了测试结果不稳定这种情况。**如果一二三段的结果是红绿红，这个测试确实在检验这个修复；如果是红绿绿，说明第一次红另有原因。**

## 门禁怎么写

### 登记表读进策略

完整 Rego 见仓库 `policy/reversibility.rego`。

未登记即最严档那条规则，是这套机制不被绕过的唯一保障。 缺了它，新增一个目录就能逃出分级，而新增目录恰恰是最常见的动作。

### 风险分级

完整 Rego 见仓库 `policy/risk.rego`。前五条是自我保护：能修改自己门禁配置的 Agent 等于没有门禁，所以工作流、技能、策略、不变量四个目录永久最严档。

### 抽检不能用随机数

R1 抽检两成，但**不能用随机数**。随机意味着无法复算，一次争议就说不清“这个 PR 当时到底该不该被抽中”。完整实现见仓库 `tools/orchestrator/sampling.py`。

三个性质：**可复算**（任何人拿提交哈希都能算出同样结果）、**周内稳定**（重跑 CI 不会改变抽检结论，避免反复触发直到不被抽中）、**跨周轮转**（同一个长期分支不会永远逃过抽检）。抽检结果连同种子写进审计包，事后可核。

## 状态存在哪

这是最容易做乱的一块。原则：能入库的入库，入库的才可评审；高频写的放外部，避免提交噪声。

| 状态 | 存哪 | 为什么 |
| --- | --- | --- |
| 撤销成本登记表 | 入库 | 是规则，必须可评审可回滚 |
| 策略、技能、契约、评测样本 | 入库 | 同上 |
| 缺陷指纹库 | 入库，随 PR 提交 | 去重依据要能被审阅，避免误去重掩盖真问题 |
| 令牌预算计数器 | 外部键值存储或 Actions 变量 | 每次运行都写，入库会产生大量噪声提交 |
| 影子运行记录 | 构建产物加一份周汇总入库 | 明细体量大，结论要留痕 |
| 审计包 | 对象存储，写入即签名 | 不可变，且体量大 |
| 执行轨迹 | 可观测后端，内容外置只存引用 | 控制体积，也把脱敏收窄到一个地方 |

指纹库入库这条值得展开。 探索类角色发现问题后要去重，去重依据是指纹（平台、页面、错误签名、触发序列的哈希）。如果指纹库存在外部数据库里，某天一个真问题被误判成重复而丢弃，没有人查得出来是哪条指纹干的。入库之后，每一次去重规则的变化都出现在 PR diff 里。

预算计数器反过来：它每次运行都要写，入库会把提交历史淹掉，而且它的历史价值很低。

# 收尾

## 一条需求走完全程

用 Kite 的一个真实小需求走完全程：**多设备冲突时给用户一个提示。**

**第一步，意图澄清。** 界面相关的需求走交互设计技能的提问阶段，问出四件事：提示出现在哪一层（页内横幅还是弹窗）、能不能忽略、多久消失、离线时是否也提示。人回答四个问题，约五分钟。

**第二步，编译成需求条款。** 输出候选条款，人接受：

```markdown
[REQ-SYNC-HINT] 正文冲突合并后 MUST 在笔记详情页显示可忽略的冲突提示。
[REQ-SYNC-HINT-PERSIST] 提示 MUST 在用户手动忽略前持续存在，MUST NOT 自动消失。
[REQ-SYNC-HINT-OFFLINE] 离线状态下 SHOULD 同样显示提示。
```

**第三步，页面规约新增一态。** 详情页的状态矩阵从七种变成八种，桥接工具据此生成一条 golden 测试义务。

**第四步，落成任务契约。** 边界锁定四个文件：两个实现、两个测试。风险分级预判为 R1。

**第五步，实现。** 实现者在边界内改代码，测试编写者在独立工作树里按义务写测试，看不到实现。两者的产出由编排层落盘。

**第六步，验证。** 契约执行全绿，边界无越界，回归有效性验证走完红绿红三段，变异测试得分未下滑。

**第七步，合并门。** 策略判定 R1，确定性抽检按提交哈希算出未命中，自动合并。抽检结果与种子写进审计包。

**第八步，发布。** 变更触及 `config/sdui/**` 与 `apps/mobile/lib/**` 两类路径，登记表取最严的一档，客户端那部分走 D1 等下次发版，下发部分走 D1.5 自动放行，观察十分钟指标。

全程人参与两次：第一步回答四个问题，第二步接受需求条款，合计不到十分钟。

把三道关卡标在这条链上，各等级下哪几道是开的就一目了然：

| 关卡 | 在第几步 | L1 | L1.5 | L2 | L3 |
| --- | --- | --- | --- | --- | --- |
| 需求接受 | 第二步 | 开 | 开 | 开 | 关 |
| PR 合并 | 第七步 | 开 | 按风险抽样 | 关 | 关 |
| 发布按钮 | 第八步 | 开 | 下发部分关，二进制开 | 同左 | 同左 |

上面这条链跑的是 `L2 / D1.5`：需求那道门开着，PR 那道靠抽检概率性地开，发布那道对下发内容关、对客户端二进制开。**同一次变更在两条轴上处于不同等级，这是常态，不是配置错误。**

这条链也暴露了它自己的薄弱处。 第七步那个“抽检未命中所以自动合并”，是整条链上唯一一个既无人也无确定性证据的环节：抽检算法是确定性的，但抽检这件事本身是概率性的兜底。它的正当性完全来自 R1 这个分级判断准不准。**所以风险分级规则是这套体系里最该被认真评审、也最该定期回看的东西**，比任何一个技能都重要。

## 把这套方法带走：一个不断迭代的 Skill

前面建的是 kite 一个项目的 L1 到 L3。但这套方法的价值不在 kite，在它能被带走：第二个项目、另一种语言栈、另一个团队。每多跑一个项目，方法的边界就被撑宽一点，哪些是普适的、哪些是项目特定的，才看得清。

抽象的形态选 Skill 而不是脚手架或库，是因为这套方法的主体是**判断与决策**（什么时候建契约、什么时候升 L1.5、deny 了怎么办），不是确定性流程。Skill 把方法装进 agent 的操作回路里，让 agent 在新项目按方法做决策，而不是机械套模板。

### 抽象对象要分三层

不是所有东西都用同一种方式抽象。按确定性要求分三层：

| 层 | 例子 | 抽象方式 |
| --- | --- | --- |
| 理念 | 规约驱动、五态、风险分级、审计 | 写进 `REFERENCE.md`，纯文档，任何项目直接用 |
| 配置 | `risk.rego` 的 R3 路径与白名单、`verify.yml`、spec 骨架、AI-BOM 组件清单 | 模板 + 提示词现场生成（项目特定，本就要改） |
| 复杂确定性工具 | spec-runner（五态 gate / boundary / contract 解析 / risk / audit-seal） | 行为 spec + 参考实现（见下） |
| 语言无关件 | `risk.rego` 策略本身、opa、agent-spec | 直接复用，不抽象 |

关键判断：**spec-runner 不能纯提示词生成**。五态定义、退出码、`risk.rego` 的 input 格式是跨项目契约，每次让模型重新写一遍会漂移——pass/fail 的边界、deny 的语义对不齐，L1.5 的关卡概率化就失效。所以它要一份**行为规约**（该有哪些子命令、每个的输入输出与退出码、五态与 input 的精确定义），agent 按规约生成实现，再用规约里的测试验证行为一致。

### Skill 的结构

```
l1-foundation/
├── SKILL.md              # 在新项目建立 L1/L1.5 的步骤 + 决策点
├── spec-runner.spec.md   # spec-runner 的行为规约（CLI 接口/五态/退出码/input 格式）
├── reference/            # Python 参考实现（kite 的，作 reference 不是唯一源）
├── templates/            # 配置模板（risk.rego / verify.yml / spec 骨架 / AI-BOM）
└── REFERENCE.md          # L1-L3 理念精要（本文的浓缩版）
```

agent 在新项目的工作：读 `SKILL.md` → 看项目语言（Python 复制 reference / 其他语言按 `spec-runner.spec.md` 重新实现 + 跑规约测试）→ 填 `templates`（`risk.rego` 的 R3 路径改成新项目的敏感目录、AI-BOM 组件换成新项目的模型与工具）→ 跑通 CI。这本身就是一次「用规约建工具」的验证——L1 的理念用来建 L1 的工具，自指但自洽。

### 不断迭代，不是一次写完

Skill 不追求一次写对所有项目。节奏跟着实践走：

1. 先写 Skill 骨架 + spec-runner 行为规约（kite 已跑通 L1 与 L1.5，规约从现成实现反推）
2. 第二个项目试用（最好是不同语言栈，逼出 reference 实现里藏着的语言假设）→ 暴露规约没写清的边角
3. 规约与模板按反馈收紧，参考实现同步
4. kite 跑到 L2 / L3 时，Skill 跟着加这两章

每跑一个项目，三层里「项目特定」的边界就往里收一点，「普适」的往外扩一点。等到第三个项目能纯靠 Skill 起步、几乎不看 kite 源码，这层抽象才算立住。

### 明确不抽象什么

不进 Skill 的：kite 的业务契约（`specs/`）、kite 的需求治理内容（`knowledge/`）、kite 的 AI-BOM 具体组件清单。这些是 kite 的，不是方法的。Skill 带走的是**怎么建这些东西的判断**，不是这些东西本身。

## 结语

第一部分讲的是撤销成本决定你能放权到哪一级，第二部分讲的是怎么把那条判断变成会阻断构建的东西。

如果只带走三样：**登记表让撤销成本从判断变成规则**，**权限配置让隔离从叮嘱变成事实**，**红绿红三段让测试有效性从相信变成验证**。

其余的都可以按自己的技术栈换掉。

## 附录二 可运行文件清单

文中的代码块，在仓库里应当是能直接改的文件，而不是只能复制的片段。建议这样摆：

```
docs/                              # 本文
examples/
├── reversibility.yaml             # 撤销成本登记表
├── policy/
│   ├── reversibility.rego         # 登记表校验：未登记落最严档、副作用不可撤销必须带上限
│   └── risk.rego                  # 风险分级 R0 到 R3、悬空选择器、边界越界
├── agents.json                    # 角色权限：读写范围、deny_read、验证者锁档
├── skills/
│   └── test-author/SKILL.md       # 隔离测试编写者
├── scripts/
│   ├── repro-gate.sh              # 红绿红三段
│   └── sampling.py                # 确定性抽检
├── workflows/
│   └── verify.yml                 # 契约验证流水线
└── specs/
    └── task-sync-conflict.spec.md # 任务契约示例
prototype/                         # 附录三那个双语言最小项目
```

摆成文件而不是代码块，有一个实际好处：**它们可以被自己的 CI 检查。** 策略文件能跑 `conftest verify`，登记表能校验 schema，契约示例能跑 lint。文档里的代码块会随着上游变化悄悄过时，仓库里的文件会红。

## 附录三 原型验证记录

规约层的可行性，在一个双语言最小项目上实测过：一条真实需求（离线笔记冲突合并）、一份任务契约、Python 与 Dart 两侧的实现和契约绑定测试，加上约五百行的执行器适配。Python 侧真实执行，Dart 侧因环境无 SDK 判不确定。

**确认开箱可用的三件事。** 结构化测试选择器是 DSL 的一等字段，`Package` 可以直接当执行器判别式，不需要命名约定；边界强制在纯 Python 仓库里零适配可用，只看路径；契约头部的风险标记会真的触发质量门禁。

**确认必须适配的一件事。** 执行器绑定 Rust 工具链，Python 与 Dart 需要外接，临时方案约三天可用。

**发现的四个坑。**

一、外接的执行结果在报告里会被标记为推断而不是机械执行，与工具自身区分证据来源的设计意图相冲突。缓解办法是另出一份机械证据文件，审计以它为准；长期应把可配置执行器贡献回上游。

二、待办文件不含测试选择器，外部执行器必须另外从契约取，按场景名对齐。

三、pytest 对不存在的测试名返回退出码 4，与真正的用法错误共用同一个码，缺失的测试文件也是 4。只看退出码会把契约缺陷伪装成环境问题。

四、把合并实现改坏（排序改成按到达顺序，破坏交换律）之后，例子级场景照样通过，只有属性级场景变红。**契约里的场景类型分布，直接决定它能拦住哪类失效。** 据此把属性级场景占比列进出口准则。
